# 📖 Orion Architecture & Codebase Reference

## 1. The High-Level Architecture

Orion is a decoupled application connected by a secure IPC (Inter-Process Communication) bridge.

* **The Frontend (`src/`):** A standard Single Page Application (SPA) built with React, TypeScript, Tailwind CSS, and Vite. It has no direct access to your file system or OS.
* **The Backend (`src-tauri/`):** A native Windows binary written in Rust using Tauri v2, `tokio` (for async execution), and `rusqlite` (for SQLite database management).
* **The Bridge (`invoke`):** The React frontend sends JSON payloads via `invoke("command_name")` to Rust. Rust does the heavy lifting, serializes the response, and sends it back to React.

## 2. Codebase Map (Where things live)

### 🦀 The Rust Backend (`src-tauri/src/`)

* **`lib.rs`:** The central hub. This is where the Tauri application is built, plugins (updater, autostart, single-instance) are registered, and all IPC commands are exposed to the frontend via `invoke_handler`.
* **`db.rs`:** The SQLite database engine. It contains the schema definition inside the `MIGRATIONS` array and the `initialize()` function that creates the `data.db` file in the user's `%LOCALAPPDATA%`.
* **`models.rs`:** The Rust structs that define the shape of your data. Notice the `#[derive(Serialize, Deserialize)]` macros—these are what allow Rust to automatically translate data to and from JSON for the React frontend.
* **`commands.rs`:** The heaviest file in the app. It contains the actual logic for every function React can call. It handles CRUD operations for the database and the OS-level script execution (`tokio::process::Command`).
* **`tray.rs`:** Manages the system tray icon, context menus, and the global keyboard shortcut that summons the Spotlight window. The shortcut is registered at *runtime* from the `spotlight_shortcut` row in `app_settings`, not at plugin-build time, because Settings can change it.
* **`ai.rs`:** Local sentence embeddings. Runs `all-MiniLM-L6-v2` (384-dim) through `candle` on the CPU — no ONNX Runtime DLL, no Python. The ~90 MB weights are downloaded once into the *local* app data directory and reused offline afterwards. `generate_embedding` is blocking and CPU-bound: always call it from `spawn_blocking`.
* **`alert.rs`:** The timer alert window. Orion's own frameless always-on-top notification, because a Windows toast can be delivered and still never draw a banner, with no way for the app to detect it.

### ⚛️ The React Frontend (`src/`)

* **`App.tsx`:** The root controller. It determines which window is rendering (Main UI vs. Spotlight) using `getCurrentWebviewWindow().label`. It also holds the **Global Timer State** so timers keep ticking across workspaces.
* **`api/` directory:** These are wrapper functions around Tauri's `invoke`. Instead of calling `invoke("get_workspaces")` directly in your components, you call `getWorkspaces()` from this folder, ensuring strict TypeScript typing.
* **`types.ts`:** The exact TypeScript mirrors of the Rust structs in `models.rs`.
* **`components/` directory:** The modular UI elements (`SettingsView`, `Spotlight`, `TimerWidget`, `TimerAlert`, `ShortcutInput`, `ResourceSuggestions`, etc.). `App.tsx` decides which of the three windows — `main`, `spotlight`, `alert` — is being rendered.
* **`utils/` directory:** Framework-free helpers, each with its own tests: `reorder.ts` (drag-and-drop index arithmetic), `paths.ts` (`file://` URL to native path), `notify.ts`, `version.ts`.

## 3. Core Mechanics & "Gotchas" (Must-Know)

### The Async/Blocking Divide (`spawn_blocking`)

You will notice the agent wrapped almost every database operation in `commands.rs` inside `spawn_blocking(move || { ... })`.

* **Why?** Tauri uses `tokio` for asynchronous tasks. However, `rusqlite` is a synchronous (blocking) library. If you run a heavy database query or a heavy JSON export on the main async thread, the entire app (and UI) will freeze. `spawn_blocking` pushes the heavy DB work to a separate background thread pool, keeping the app lightning-fast.

### The Script Execution Engine

When executing Python, Node, or WSL bash scripts, the app does not blindly run code.

* It writes the script content to a temporary file in `%TEMP%`.
* It calls the interpreter (e.g., `python.exe`) against that temp file.
* **WSL Interop:** Windows does not pass environment variables to Linux. The agent specifically builds a `WSLENV` string with `/u` flags to force variables like API keys into the WSL guest.
* **Output limits:** The backend truncates output to 64KB (`MAX_OUTPUT_CHARS`). If you run a data pipeline that dumps massive logs, it won't crash the React UI trying to render it.

### The Vector Index

`vec_items` is a `sqlite-vec` virtual table living inside the same `data.db`, so one file remains a complete backup. Two consequences worth knowing:

* **A virtual table cannot carry a foreign key.** Nothing cascades into it, so every delete path clears its vectors explicitly, and `import_data` wipes the whole index because it cannot be kept in step any other way.
* **`sqlite-vec` is compiled into the binary** and registered as a static auto-extension *before* the first `Connection::open`. There is no `.dll`/`.so` to ship per platform, but the registration order matters: a connection opened before it is registered will not have `vec0`.

KNN always returns the k nearest vectors with no notion of relevance, so anything ranking results has to apply its own distance cut-off — see `SEMANTIC_SUGGESTION_MAX_DISTANCE`.

### Window Management & Single Instance

Orion has three windows defined in `tauri.conf.json`: `main` (hidden by default), `spotlight` (transparent, frameless) and `alert` (transparent, frameless, always on top, never focused). `main` is also measured against its monitor's work area at startup and shrunk if it does not fit — the configured size is *logical*, so on a scaled display it can exceed the usable screen.

* When the user clicks the "X" on the main window, `lib.rs` intercepts `WindowEvent::CloseRequested` and hides the window instead of killing the process.
* `tauri-plugin-single-instance` intercepts secondary launches, drops them with exit code 0, and surfaces the hidden primary window.

## 4. Implementing TDD (Test-Driven Development)

To enforce quality as you prepare for commercialization, you need to test the Rust backend and the React frontend separately.

### A. Testing the Rust Backend (Logic & Database)

You can write unit tests directly in your Rust files. Rust's built-in testing framework is exceptional. You do not need to boot the Tauri UI to test your database logic.

**Gotcha: use `db::open_test_connection()`, not `Connection::open_in_memory()`.** `sqlite-vec` registers as an auto-extension that only applies to connections opened *afterwards*, so a plain in-memory connection has no `vec0` and `init_schema` fails when it reaches the `vec_items` migration. `open_test_connection` does the registration first and is what every test in the tree uses.

**Example: a migration test:**

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use rusqlite::Connection;

    #[test]
    fn test_database_initialization() {
        // Use an in-memory SQLite database for testing, so it doesn't touch the disk
        let mut conn = Connection::open_in_memory().unwrap();
    
        // Execute migrations
        for migration in MIGRATIONS {
            conn.execute_batch(migration).expect("Migration failed");
        }

        // Verify the tasks table exists
        let mut stmt = conn.prepare("SELECT name FROM sqlite_master WHERE type='table' AND name='tasks'").unwrap();
        let exists = stmt.exists([]).unwrap();
        assert!(exists, "Tasks table should be created by migrations");
    }
}

```

Run `cargo test` in the `src-tauri` directory to execute backend tests.

### B. Testing the React Frontend

To test React components without booting the Rust backend, you use **Vitest** and **React Testing Library**.

* **The Challenge:** Your React code calls `invoke()`, which normally requires the Rust backend.
* **The Solution:** Use `@tauri-apps/api/mocks` to intercept `invoke` calls and return dummy data during tests.

**Example: Testing a component that loads workspaces:**

```typescript
import { render, screen } from '@testing-library/react';
import { mockIPC } from '@tauri-apps/api/mocks';
import App from '../App';

test('renders workspaces from the backend', async () => {
  // Mock the Rust backend response
  mockIPC((cmd, args) => {
    if (cmd === 'get_workspaces') {
      return [{ id: '1', name: 'Data Pipeline', color: '#ff0000', sortOrder: 0 }];
    }
  });

  render(<App />);
  
  // Assert the mocked workspace appears on screen
  expect(await screen.findByText('Data Pipeline')).toBeInTheDocument();
});

```

## 5. Next Steps for Commercial Ownership

As you familiarize yourself with the code, tackle these refactoring and operational steps:

1. **Read `commands.rs` line-by-line:** Understand exactly how `launch_resource` and `execute_script` build their commands. This is the core security perimeter of your app.
2. ~~**Setup Vitest**~~ — done. `npm test` runs the frontend suite; `cargo test` (in `src-tauri`) runs the backend one, and `cargo test -- --ignored` additionally runs the tests that need the real embedding weights.
3. ~~**Database Versioning Strategy**~~ — done. `PRAGMA user_version` is tracked in `db.rs`: `SCHEMA_VERSION` plus a matching block in `apply_versioned_migrations`. The base `MIGRATIONS` array only ever runs `CREATE TABLE IF NOT EXISTS`, so it cannot alter an existing table — any change to one needs a new versioned step.
4. **Cross-platform, if a macOS build is ever wanted.** `commands.rs` currently has no `#[cfg]` attributes and calls `creation_flags`, `explorer.exe`, `wt`, `cmd /C start` and hardcoded browser paths directly, so it will not compile off Windows. That is a platform-abstraction refactor rather than a port, and it gets harder with every feature added first.
